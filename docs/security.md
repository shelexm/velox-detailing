# Безопасность

## Вход в панель студии

- Публичной регистрации нет. Первый пользователь создаётся командой (пароль вводится интерактивно и нигде не печатается):
  ```sh
  docker compose run --rm api python -m app.cli create-admin --email owner@example.com --name "Имя Фамилия"
  ```
  Смена пароля: та же команда с `--reset-password` (все сессии пользователя отзываются). Неинтерактивно можно передать пароль через переменную `ADMIN_PASSWORD`.
- Пароли хешируются Argon2id (`argon2-cffi`), минимальная длина 12 символов. При неизвестном e-mail проверяется фиктивный хеш, чтобы время ответа не выдавало существование пользователя. Ответ одинаковый для неверного e-mail, пароля и отключённого пользователя.
- Сессии серверные: в браузере cookie `velox_session` (HttpOnly, SameSite=Lax, Secure при HTTPS), в базе только SHA-256 токена. Срок жизни `SESSION_TTL_HOURS` (по умолчанию 12 ч). Выход отзывает сессию в базе.
- CSRF: при входе выдаётся отдельный токен (cookie `velox_csrf`, читается скриптом панели). Любой изменяющий запрос панели должен прислать его в заголовке `X-CSRF-Token`; сервер сравнивает с хешем, привязанным к сессии. Дополнительно запросы с чужим заголовком `Origin` отклоняются.
- Ограничение попыток входа за 15 минут, затем HTTP 429: 5 неудачных попыток на пару «e-mail и IP» (так посторонний не может закрыть вход владельцу со своего адреса), 40 на один e-mail со всех адресов вместе и 20 с одного IP. Хеш пароля (Argon2) считается в потоке, не больше двух одновременно.

## Роли и изоляция студий

- Роли в студии: `owner` (всё, включая настройки и контакты), `admin` (записи, клиенты, услуги, расписание, контент), `master` (только свои записи, без изменений).
- Все маршруты панели имеют вид `/api/v1/admin/studios/{studio_id}/...` и проверяют членство пользователя в этой студии. Не участник студии получает 404, чтобы нельзя было перебирать идентификаторы.
- Каждый запрос к данным фильтруется по `studio_id`. Связи записи с услугой, мастером, боксом и клиентом в базе идут через составные внешние ключи `(studio_id, id)`: запись физически не может сослаться на объект другой студии.

## Публичная запись

- Без входа доступны только данные для формы: услуги, свободное время, создание заявки и управление своей заявкой по секретной ссылке (токен хранится в базе в виде хеша).
- Создание заявки: не больше 10 запросов с IP за 10 минут, скрытое поле-ловушка для ботов, обязательное согласие на обработку персональных данных (время и версия согласия сохраняются у клиента).
- Ошибки валидации называют поле, но не повторяют введённые значения.

См. `docs/booking-model.md`: блокировка строки студии в транзакции и ограничения `EXCLUDE USING gist` в PostgreSQL.

## Заголовки и ошибки

- `Content-Security-Policy` без inline-скриптов (`script-src 'self'`), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, HSTS при HTTPS, `Cache-Control: no-store` для панели, `X-Robots-Tag: noindex` для `/admin`.
- Документация API (`/api/docs`) отключена при `APP_ENV=production`.
- Необработанные исключения пишутся в лог с трассировкой, пользователь получает только код ошибки и `request_id`.
- `TrustedHostMiddleware`: приложение отвечает только хостам из `ALLOWED_HOSTS`.

## Логи и персональные данные

- Строки логов проходят маскировку: телефоны (остаются две последние цифры), токены Telegram, пары `password=`, `token=`, `secret=`, `cookie=`.
- Outbox уведомлений хранит только идентификаторы записи; тексты собираются в момент отправки.

## Удаление данных клиента (152-ФЗ)

- Владелец студии в карточке клиента: «Удалить персональные данные» (`DELETE /api/v1/admin/studios/{id}/clients/{client_id}`,
  только роль owner). Пока у клиента есть активные записи (новая или подтверждённая), удаление не выполняется.
- Удаляются карточка (имя, телефон, Telegram, заметки, метки, согласие), автомобили клиента, свободный текст его
  записей (имя в заявке, автомобиль, комментарии, причина отмены), данные в истории событий и очередь уведомлений.
  Прошлые визиты остаются для статистики без привязки к человеку (дата, услуга, цена, мастер, бокс, статус).
- Резервные копии содержат старые данные до удаления по сроку (`BACKUP_KEEP_DAYS`, по умолчанию 14 дней).
  Сообщения, уже отправленные в чат администраторов Telegram, удаляются вручную в самом чате.
- Проверочная база после `scripts/restore.sh` (режим проверки) удаляется сразу после сравнения, чтобы копии
  персональных данных не оставались на сервере.
- Хранение персональных данных граждан РФ: по 152-ФЗ базу нужно держать на сервере в России
  (учитывается при выборе VPS).

## Секреты

- Все секреты только в `.env` (в Git не попадает, `.dockerignore` исключает его из образа). В `.env.example` только заглушки.
- Настройки с секретами имеют тип `SecretStr` и не выводятся в `repr` и логах.

## Ограничения текущей версии

- Счётчики rate limit хранятся в памяти процесса API. Это корректно для одного процесса `api`. Если запускать несколько реплик, счётчики нужно перенести в общее хранилище (например Redis).
- `FORWARDED_ALLOW_IPS="*"` безопасен, пока порт API опубликован только на `127.0.0.1` (так в `compose.yaml`): заголовки `X-Forwarded-*` может прислать только локальный прокси или туннель.
