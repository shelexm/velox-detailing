# Архитектура

Один репозиторий, один образ приложения `velox-app`, несколько процессов в Docker Compose. Сайт, панель,
API и бот используют одни и те же сервисы бизнес-логики и одну базу PostgreSQL.

## Процессы

| Сервис | Что делает |
|---|---|
| `db` | PostgreSQL 17 (`postgres:17-alpine`), данные в томе `velox_pgdata`; порт наружу не публикуется |
| `media-init` | один раз при запуске отдаёт том фото пользователю приложения |
| `migrate` | один раз при запуске: `alembic upgrade head` и идемпотентные стартовые данные (`python -m app.cli seed`); единственный, кто меняет схему |
| `api` | FastAPI (uvicorn): сайт (Jinja2), панель, публичное и админское API, календарь для Telegram, раздача фото |
| `bot` | aiogram 3 (long polling) и воркер очереди уведомлений и напоминаний; без `TELEGRAM_BOT_TOKEN` сразу завершается |
| `backup` | раз в сутки `pg_dump` и архив фото с ротацией (`scripts/backup-loop.sh`) |

`api` и `bot` стартуют только после успешного `migrate`. Все сервисы с ротацией логов (5 по 10 МБ).

```
браузер ──HTTPS──> nginx ──> api ───────┐
Telegram <──────── bot ─────────────────┼──> PostgreSQL
                    └ воркер outbox ─────┘
                       backup ── pg_dump ──> /opt/velox/backups
```

## Слои кода

```
app/core/       настройки (pydantic-settings), безопасность (пароли argon2, сессии, CSRF, CSP), единый формат
                ошибок, логи с маскировкой, телефоны, Telegram (подпись initData, владелец удержания)
app/db/         асинхронный движок SQLAlchemy, сессия на запрос, связь с Alembic
app/models/     таблицы (ниже)
app/schemas/    Pydantic-схемы запросов и ответов API
app/services/   бизнес-логика:
                  availability  чистые функции расчёта свободного времени (без базы)
                  booking       единственная точка создания, удержания, переноса, смены статуса записей
                  queries/stats чтение для панели и сайта, статистика
                  catalog, staff, schedule, media, clients, privacy, outbox, auth, calendar (.ics)
app/content/    Pydantic-схемы блоков сайта: по ним проверяется сохранение и строятся формы панели
app/api/routes/ HTTP API: public, auth, admin_* (по разделам), tg, health
app/web/        страницы сайта (site.py) и панели (panel/*), подключение шаблонов и статики
app/templates/  Jinja2: site/ (сайт и его блоки), panel/ (панель), tg/ (календарь)
app/bot/        handlers, keyboards, texts, logic, render (тексты уведомлений), worker, notifier
app/seed/       стартовые данные: студия, каталог и цены из макетов, тексты блоков, фото
app/cli.py      команды seed и create-admin
```

Правило: маршруты API, страницы панели и бот не работают с базой напрямую в обход сервисов, когда речь
о записях; любое занятие времени идёт через `app/services/booking.py`.

## Модель данных

| Группа | Таблицы |
|---|---|
| Студия | `studios` (контакты, реквизиты, бренд и логотип, правила записи, чат администраторов, счётчик номеров записей) |
| Доступ | `users`, `studio_memberships` (роль в студии), `user_sessions` (хеши токена сессии и CSRF) |
| Каталог | `service_categories` (разделы прайса), `service_groups` (направления на сайте), `services`, `service_staff` |
| Люди и места | `staff` (мастера), `resources` (боксы, места) |
| Расписание | `studio_hours`, `studio_breaks`, `special_days`, `staff_hours`, `staff_absences`, `time_blocks` |
| Клиенты | `clients` (телефон уникален в студии, Telegram, согласие на ПД), `vehicles` |
| Записи | `bookings` (номер, клиент, услуга, мастер, бокс, время, `occupancy`, статус, источник, снимок цены и названия, версия), `booking_events` (история), `notification_outbox` (очередь уведомлений) |
| Сайт | `site_sections` (блоки главной: видимость, порядок, содержимое JSONB по схеме), `portfolio_cases`, `reviews`, `gift_options`, `media_assets` |

Защита от двойной записи: блокировка строки студии и ограничения `EXCLUDE USING gist` по мастеру и боксу
(подробно: [booking-model.md](booking-model.md)).

## Мультиарендность

Каждая таблица студии содержит `studio_id`; связи записи с клиентом, услугой, мастером и боксом идут через
составные внешние ключи `(studio_id, id)`: мастера, бокс или услугу другой студии к записи не прикрепить даже
прямым SQL. Доступ к панели и API проверяет членство пользователя в студии; чужая студия отвечает 404.
Сайт и бот обслуживают студию `DEFAULT_STUDIO_SLUG`.

## Путь запроса

1. **nginx** завершает TLS и передаёт реальный IP посетителя в `X-Forwarded-For`.
2. **RequestIdMiddleware:** у каждого запроса `X-Request-ID` (в логах и в ответе, в том числе в ошибках).
3. **SecurityHeadersMiddleware:** CSP (`script-src 'self'`, для `/tg/` ещё `telegram.org` и встраивание в
   web.telegram.org), HSTS, `nosniff`, `Referrer-Policy`, запрет встраивания; для панели `noindex` и `no-store`.
4. **TrustedHostMiddleware:** запросы с чужим `Host` отклоняются (`ALLOWED_HOSTS`).
5. Зависимости маршрута: сессия базы, текущая студия, проверка входа, роли, CSRF и `Origin`, ограничение
   частоты по IP.
6. Сервис выполняет действие в транзакции; ошибки бизнес-правил превращаются в JSON `{"error": {...}}`.

## Уведомления

Сервис записи кладёт событие в `notification_outbox` в той же транзакции, что и изменение записи (только
идентификаторы, без персональных данных). Воркер в процессе `bot` забирает строки через
`SELECT ... FOR UPDATE SKIP LOCKED`, собирает текст в момент отправки, отправляет через Telegram и повторяет
с растущей паузой (до 8 попыток). Сбой Telegram не влияет на запись. Напоминания за 24 и 2 часа планирует
тот же воркер, с ключом против повторной отправки.

## Фото

Загрузка через панель: проверка декодированием (Pillow), до 5 МБ и ограничение по числу пикселей,
перекодирование с удалением метаданных, случайные имена. Публикуются варианты шириной 480, 960, 1600 и 2400
пикселей в AVIF, WebP и JPEG; сайт отдаёт `<picture>` с `srcset`. Оригинал хранится отдельно и наружу не
раздаётся. Место использования каждого фото известно (`media.usage_map`), поэтому используемое фото нельзя
удалить, а замена файла обновляет все места сразу.

## Контент сайта

Шаблоны главной не содержат текстов: каждый блок (`hero`, `services`, ..., `seo`) читает своё содержимое из
`site_sections.content`, проверенное Pydantic-схемой из `app/content/sections.py`. По той же схеме панель
строит форму блока. Стартовые тексты из макетов (`app/seed/content.py`) записываются только если блока ещё нет,
поэтому правки в панели не перезаписываются при обновлениях.

## Конфигурация

Всё из `.env` ([configuration.md](configuration.md)). Переход на другой домен: поменять `PUBLIC_BASE_URL` и
`ALLOWED_HOSTS`, перезапустить `api` и `bot`, без пересборки.

## Тесты и CI

pytest на отдельной базе `_test` (unit, integration, api, bot), ruff, GitHub Actions на каждый push
([development.md](development.md)).
